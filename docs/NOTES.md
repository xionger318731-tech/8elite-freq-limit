# 开发笔记

记录这个模块开发过程中被实测推翻的假设，以及最终方案的由来。

---

## 一、被推翻的三个方案

### 方案 A：用 `run_delay` 判断"算力不足"（已废弃）

**想法**：`/proc/{pid}/schedstat` 第二个字段是"进程就绪但拿不到 CPU"的累计时间。
如果限频导致进程被饿，这个值应该会涨。

**实测**（本机，绑单核）：

| 频率 | 0 个竞争者 | 1 个 | 2 个 | 3 个 |
|---|---|---|---|---|
| 2400000 | 0 ms | 9 ms（60%）| 10 ms（71%）| 7 ms（65%）|
| 1785600 | 0 ms | 9 ms（57%）| 14 ms（72%）| 31 ms（80%）|
| 1363200 | 0 ms | 12 ms（57%）| 26 ms（72%）| 26 ms（72%）|

**结论**：`run_delay` 只跟"核心是否被抢"有关，**跟频率无关**。
单核降频时进程照样独占核心，只是跑得慢，不会被饿。

---

### 方案 B：用 `dumpsys gfxinfo` 掉帧率做反馈（已废弃）

**想法**：`Number Slow UI thread` 和 `Number Slow issue draw commands`
是 Android 自己统计的"UI 线程算不完"次数，最接近用户感知。

**实测**：
- 静态页面时这些值恒为 0（干净）
- 但单次 `dumpsys gfxinfo` 调用对重负载 app 要 **4.5 ~ 5 秒**

**致命问题**：如果轮询周期 10 秒，那有 5 秒在 `system_server` 里跑 gfxinfo，
**占空比 50%**。为了测卡顿，自己制造了卡顿。

**结论**：作为诊断工具可以，作为实时反馈信号不可行。

---

### 方案 C：用触摸事件判断"静止"（已废弃）

**想法**：`getevent -l /dev/input/event9` 监听触摸，手指离开屏幕就是静止。

**实测**（30 秒完全不操作屏幕）：

```
DOWN=20  UP=20
压力值: 3, 4, 6（极低）
无 ABS_MT_POSITION_X/Y 坐标
```

**结论**：本机触摸屏有幽灵触摸，30 秒 20 次误报。
如果用它当信号，会永远判定"正在触摸"，永远不降频。

（尝试过用"DOWN 后 200ms 内是否有坐标"过滤，仍然失败——
微信小程序等场景会持续产生完整触摸序列。）

## 二、被判据推翻的中间方案：CPU 有效频率

**先说一个被推翻的中间方案：有效频率**

V1.0 曾用「CPU0 有效频率」作为判据：

```
有效频率 = Σ(档位频率 × 该档驻留增量) / Σ(驻留增量)
```

实测 `time_in_state` 语义（本机）：
- 16 档、单位 10ms、**只统计 policy 首核（CPU0）**
- 验证：绑 CPU0 满载 10 秒 → 该档 +979 ticks（≈1000 = 10s × 100Hz）

**但这个方案有致命缺陷**：

一旦把上限压到 748800，CPU 满载也只能跑 748800，
有效频率 = 748800，占比 = 100%。
空载和满载看起来完全一样。

实测证据（压到 748800 后测撞顶率）：

| 场景 | 撞顶率 |
|---|---|
| 空载 | 100% |
| 单核满载 | 100% |
| 8 核满载 | 100% |

→ 频率信号在被限制后完全失效，只能逐档试探升频，这就是 V1.0 响应慢（3 秒）的根源。

## 二·补、V1.2 的判据：CPU 使用率（V1.3 已被替换，见第七节）

> 本节记录 V1.2 为什么选 CPU 使用率。它在**限频侧**确实优于有效频率，
> 但在**负载侧会饱和**（满载恒 100%），V1.3 因此改为需求密度 + 撞顶率双判据。

**为什么这个信号可靠**：

CPU 使用率是「时间维度」的，不受频率限制影响。
满载时 CPU 100% 时间在跑，空载时大部分时间在 idle——
不管频率是多少，这个比例都成立。

**实测验证**（不同上限下 8 核满载）：

| 上限 | 满载使用率 | 空载使用率 |
|---|---|---|
| 2227200 | 100% | 22.9% |
| 1785600 | 100% | 50.2% |
| 1152000 | 100% | 53.3% |
| 748800 | **100%** | 32.5% |

满载恒为 100%，与上限无关。

**公式：目标频率 = 当前频率 × (使用率 / 目标使用率)²**

用平方而非线性，因为饱和说明严重不足：

```
使用率 100%, 目标 50% → 4.0x  翻四倍
使用率  70%, 目标 50% → 1.96x 翻倍
使用率  50%, 目标 50% → 1.0x  不变
使用率  30%, 目标 50% → 0.36x 降档
```

**读取成本**：`/proc/stat` 一次 awk，约 2ms。

## 三、冷启动拐点实测

这是"省电 vs 流畅"的平衡依据：

| 大核上限 | 冷启动耗时 | 相对官方 |
|---|---|---|
| 官方 2.4G | 441 ms | 基准 |
| 2.4G | 455 ms | 1.03x |
| 2.0G | 536 ms | 1.22x |
| 1.78G | 584 ms | 1.32x |
| 1.15G | 678 ms | 1.54x |
| 748M | 950 ms | 2.15x |
| 384M | 2265 ms | 5.1x |

**结论**：2.4 GHz 是真正的无损点。低于它开始明显变慢。

所以冷启动保护锁 **2.4 GHz**，不是完全放开（完全放开会被官方拉到 3.5G，白费电）。

## 四、踩过的 bug

### 1. `read -r f _` 在 busybox 下有 bug

```bash
while read -r f _; do ... done < file   # 全部返回 384000（错）
for f in $(cat file); do ... done       # 正确
```

这个 bug 曾把大核一路压到最低档。

### 2. `time_in_state` 行数不匹配导致算错

```bash
awk 'NR==FNR{a[FNR]=$2;next}{d=$2-a[FNR]...}'
# 两次采样行数不同时 a[FNR] 为空 → 输出 1909915（错）
```

修复：`if (FNR > n || !(FNR in a)) next`

### 3. 时钟竞态导致负数

触摸时间戳可能比当前时间大，`-31 < 700` 恒真 → 永远判定"正在触摸"。

### 4. 卸载时顺序错误

先杀 daemon 再杀 watchdog → watchdog 60 秒后把 daemon 拉回来，
导致"卸载了但还在限频"。

修复：**必须先杀 watchdog**。

### 5. 卸载脚本误杀自己

用 `*eta_sched*` 模糊匹配进程名，把执行卸载脚本的 shell 自己也匹配上了。

修复：精确匹配 `"sh /data/adb/eta_sched/<name>.sh"`。

### 6. KSU WebUI 的 exec 签名

```javascript
// 错：第三个参数传函数
ksu.exec(cmd, '{}', (errno, stdout) => {...})

// 对：第三个参数是全局回调函数的名字（字符串）
ksu.exec(cmd, JSON.stringify({cwd:'/'}), 'cb_xxx')
window['cb_xxx'] = (errno, stdout, stderr) => {...}
```

传函数会导致永远不回调，页面一直转圈。

## 五、性能优化过程

| 版本 | 开销 | 做法 |
|---|---|---|
| v4.0 | 0.300% | 250ms 循环，5 fork/轮 |
| v4.1 | 0.244% | 500ms 循环 |
| **V1.0** | **0.165%** | 1000ms 循环 + 频率表缓存 |

**根因分析**：`utime=41, stime=242` → 开销几乎全在 fork/exec，不是计算。

所以优化方向是**减少 fork 次数**，不是优化算法。

## 六、未采用的思路

### P95 分位统计

有些调度方案用 P95 分位频率做学习判据。我没用，因为：

- 需要长时间窗口累积，响应慢
- 对"瞬时需求"不敏感
- 有效频率（加权平均）已经能反映需求

### 超大核 core_ctl 控制

用 `core_ctl` 让超大核离线，比限上限更省电。但：

- 离线/上线有延迟，影响突发响应
- 和官方 hotplug 策略可能冲突

本模块只用 `cooling_device` 控上限，不动 hotplug。

### 按 app 学习（V1.0 时代的判据式学习）

曾经实现过（v1.x 自学习版），但：

- 需要每个 app 在多个频率档攒够证据才激活
- 官方档位切换不受控制，可能永远凑不齐
- 结果"装了等于没装"

**结论**：把它当**判据**不可行，开箱即用的动态跟随更实用。

**V1.3 折中方案**：学习不再参与判据，只记"该包稳定收敛后的 cap"。
切回应用时用它做伺服初值，跳过爬升过程——不学习也能跑，学到的只是省掉重收敛。

## 七、V1.3：控制律重写（DCS）

### 为什么推翻 V1.2 的平方律

```
V1.2:  cap(n+1) = 读回节点 × (使用率 / 目标)²
```

四个问题叠在一起：

1. **乘性随机游走，无绝对锚点**：以回读节点为基准，每一轮都在上一轮的结果上乘一个系数，误差不会回归，只会累积漂移。
2. **把 sysfs 节点当迭代基准**：ColorOS `oiface` 会抢写 `scaling_max_freq`，写进去的值下一秒可能已被改掉，基准本身不可信。
3. **判据饱和**：CPU 使用率在负载侧饱和（满载恒 100%），分不清"需要 2G"和"需要 3.5G"；而在限频侧又被压制（见二节），两头都失真。
4. **升档零滤波 + 单 tick 最多 3×**：两个 tick 就冲顶，冲顶后又立刻回落，形成抖动。

### V1.3 的替换

| 位置 | V1.2 | V1.3 |
|---|---|---|
| 需求判据 | 使用率 / 目标 | `need = F_avg × 利用率 / 目标占用`（绝对量） |
| 反馈判据 | 使用率（会饱和） | 撞顶率（窗口内跑在近天花板的时间占比，不饱和） |
| 目标常数 | 固定 50% | 整机功耗外环在 35–75 自动整定 |
| 迭代基准 | 回读节点 | 内部权威 cap 副本，节点仅对账 |
| 冷启动 | 固定 15s 锁 2.4G | 触摸 / 冷启动瞬时抬频 + 按包学习初值 |

### 为什么撞顶率不饱和

撞顶率统计的是"这段时间里，CPU 有多少比例跑在 `cap × 0.9` 以上"。
天花板被压到 748MHz 时，满载撞顶率 100%；但把天花板抬到 2.7G 后，
同一个满载任务的撞顶率立刻掉到低位——**这个量随 cap 变化，所以可以做闭环**。
而使用率无论 cap 多少都是 100%，无法给出"该往哪调"的方向。

## 八、V1.3 修掉的严重 bug：watchdog 每 60 秒误杀 daemon

**现象**：限频持续抖动，日志里 daemon 每隔约一分钟就重启一次。

**根因**：两侧用了不同的时钟。

```
daemon : 写 ts=...（从未真正写入 / 或写入 epoch）
watchdog: now=$(date +%s)      ← epoch 秒
```

`date +%s` 是 epoch（约 1.7e9），而 `ts` 若为 0 或 uptime 秒（几千），
`now - ts` 恒大于 180，于是**每个周期都判定 daemon 卡死并 kill -9**。

**修复**：两侧统一改用 `/proc/uptime` 的整秒（`awk '{print int($1)}'`，零 fork），
并在脚本里写明"不许用 date +%s"，避免回归。

同类问题还有一处：旧版 `state` 文件里根本没有 `eff_big` / `ratio_big` / `temp_big` / `style` 这些键，
WebUI 和 `ctl.sh` 读的全是空值，状态显示一片空白。V1.3 重建了 state 键（`mode` / `style` / `need_big` / `sat_big` / `power` / `target` / `ts` …），
并让 ctl 与 WebUI 按同一套键对齐。

## 九、V1.4fix：为什么 WebUI 总说"服务未运行"

### 真根因：守护被系统 cgroup 冻结，不是 WebUI 的问题

现场证据：`ps` 里躺着 **9 个 daemon 实例**，全部 `wchan=do_freezer_trap`，
`cgroup = /apps/uid_10466/pid_15394`，`cgroup.freeze = 1`。

```
uid_10466 = me.weishu.kernelsu（KernelSU 管理器）
```

调用链：

1. WebUI 用 `ksu.exec` 拉起 daemon → 子进程**继承管理器自己的 app cgroup**
2. 管理器退到后台 → 系统把整个 app cgroup `cgroup.freeze=1`
3. daemon / watchdog / 触摸协程全部挂起，`state` 停止刷新
4. watchdog 醒来（它也被冻过）看到 `ts` 落后 >180s → 判定"卡死" → `kill -9`
5. `ctl.sh start` 重新拉起 → 新进程又落进**同一个冻结域** → 无限循环

`alive=1` 一直写在磁盘上的旧 state 里，所以 WebUI 一会儿显示"运行中"、
一会儿显示"未运行"，用户看到的就是"状态乱跳"。

### 修法（四层）

| 层 | 做法 |
|---|---|
| daemon 启动 | `detach_freeze()` 把自身写进 `/sys/fs/cgroup/cgroup.procs`（cgroup v2 根，init 托管），之后再 fork 的子进程都继承根 |
| daemon 主循环 | 每 10 tick `self_thaw()`：被系统挪回冻结域就自己挪出来 |
| watchdog | 先 `is_frozen()` 判 `wchan=do_freezer_trap`，命中就 `thaw()` 而不是 `kill -9`；只有"活着但状态超时"才重启 |
| ctl.sh | `_launch()` 启动前先 `_detach()`；`do_start` 遇到被冻结的旧 pid 优先解冻；`_reap_dupes()` 清历史遗留 |

### 踩到的次生 bug（都已修）

- **flock 单实例锁不可用**：daemon 会 fork 触摸协程/前台探测，fd 被子进程继承；
  守护被 `kill -9` 后锁不释放，下次启动永久抢不到锁（实测连拉 7 次全部失败退出）。
  改用 **pid + `/proc/pid/cmdline` 校验 + 冻结状态** 三重判定。
- **`/system/bin/sh` 是 32 位算术**：`1555200 × 1500 = 2.33e9` 溢出成负数
  `-1962167`，导致 `HI`（单 tick 上限）变成负值 → 满载反而降频。
  所有「频率 × 千分比」改成 `pct_mul()`：先除后乘。
- **撞顶率溢出**：`SAT_B = (PN-WTOP_B)*1000/d`，阈值随 `CAP_B` 变动时
  `PN < WTOP_B` 得负值，×1000 后直接爆掉（实测 `sat=30924400‰`）。
  改为增量裁剪到 `[0, d]`。
- **场景标签乱跳**：`RAW == CAP_B` 时没有升档动作却标 `rich_wait`，
  空载时在 boost/rich_wait 之间反复横跳。`RAW==CAP_B` 统一记 `hold`。
- **地板被击穿**：快降通道按 `-40%/tick` 连乘会算出 `469548kHz`，
  比硬件最低 OPP 还低。补了出口统一钳制 `[FLOOR_BIG, STOCK_B]` + `snap`。
- **幽灵触摸的真身**：`touch.ts` 每秒刷新，`RUSH` 永远为 1。
  原实现 `dd if=/dev/input/eventN bs=16 count=1` 在无操作时立即返回，
  每次返回都记一次"触摸"。改为用 `/proc/uptime` 前后差判"阻塞读"，
  读取耗时 < 300ms 视为噪声丢弃。

### map 表：V1.4 提交的两张表是凭空写的

V1.4 的 `map_big.conf` 声称"本机 cooling 只有 3 个有效档、state0-9=2400000、
748800/556800/384000 纯属虚构"。**逐档实测结果相反**：

```
state  0..15 → 3072000, 3072000, 3072000, 2918400, 2745600, 2400000,
                2227200, 1996800, 1785600, 1555200, 1363200, 1152000,
                 960000,  748800,  556800,  384000
```

`map_prime.conf` 声称"全部 16 档都是 1689600、无法压低"，实测：

```
state  0..15 → 3513600, 3513600, 3513600, (3513600), 3513600, 3283200,
                3072000, 2841600, 2649600, 2438400, 2246400, 1958400,
                1689600, 1401600, 1209600, 1017600
```

两张表已按实测重写。**结论：任何 map 表都必须用 `probe.sh` 在本机实测生成，
不能靠"看起来合理"填。**

## 十、V1.4fix2：把"静止落不到 748"真正修完

V1.4 的更新日志说"需求前馈单位口径错 100 倍"是主因。**那不是唯一原因，也不是真正的主因。**
逐项实测后，142 行之外还有 7 个独立 bug：

### 1. `time_in_state` 加权和 32 位溢出（**最关键**）

```
tis_scan: _t_wsum = Σ(f × j)     # 16 档 × 几十万 tick
```

实测：`Σ=5705073 ticks` 时 `_t_wsum = -339633664`（负数），
`FAVG_B = -59 kHz`。**需求信号完全失效**，一切伺服都建立在垃圾数据上。

这不是"精度不够"，是硬溢出。`(f/100)*j*100` 之类"先除后乘"也救不回来
（中间量仍是 1e10 量级）。必须交给 awk（double，可安全表示到 9e15）。

更隐蔽的是 **mksh 连大数除法都截断**：

```
$ (( 4656918643200 / 5707252 ))  →  205        # 真值 815965
```

所以 FAVG/SAT 的除法也必须放进 awk，shell 侧只做减法。

### 2. 功耗读数恒为 0mW

上一版为防溢出改成 `c/1000*(v/1000)/1000`：199µA/4.02V → 全被整数除法抹成 0。
外环于是永远认为"功耗很低"，把 TARGET 一路压到 35（最激进）。

正确折中：`(c/100) × (v/1000) / 1e4` = (0.1mA)×(mV)/1e4 = mW，
既保留 0.1mA 精度，又不会溢出（2800mA 时 28000×4022=1.1e8，安全）。

### 3. 功耗外环被 `load_cfg` 每 5 秒冲掉

`load_cfg()` 结尾无条件重算 `TARGET = TARGET_LOAD ± style_offset`，
而主循环每 5s 调一次 `load_cfg`。外环刚把 TARGET 从 45 调到 46，
5 秒后又被拍回 45。**外环形同虚设**。

修：加 `TARGET_TUNED` 标记，只有风格/基准真的变了才重算。

### 4. 无新采样时用 `CAP_REF` 顶替 `FAVG_B` → 正反馈自激

`d <= 0`（本 tick 没有 time_in_state 增量）时旧代码 `FAVG_B=$CAP_REF`。
于是 `need = CAP_REF × U / T` —— 用"自己设的上限"当"实测需求"，
`CAP_REF` 越高 need 越高，need 越高 cap 越高，自激。
实测表现就是"cap 钉在某档不动，既不升也不降"。

修：沿用上一 tick 的 FAVG_B，并置 `SKIP_SERVO=1` 跳过本轮伺服。

### 5. `state` 镜像同步写 FUSE，阻塞整个控制循环

`cat "$STATE" > "$OBS/state"` 每 5 tick 同步执行一次。
`/storage/emulated` 是 FUSE，一旦 I/O 卡住，**整个决策循环停摆**。
这正是更新日志里"WebUI 报服务未运行"的第二个来源（第一个是 cgroup 冻结）。

修：每 25 tick 才镜像一次 + fork 到后台 + `.mirror.busy` 防重入。

### 6. `.fg.busy` 残留 → 前台探测永久停摆

`probe_fg()` 用 `.fg.busy` 做"探测中"标记。探测子进程被 `kill -9` 时
标记不会清 → 之后每次 `probe_fg` 都直接 return → **前台包名永远不更新** →
`games.list` 不生效、切应用不抬频、`on_fg_change` 永不触发。

修：标记文件写入 uptime 秒，超过 15s 视为残留自动清理。

### 7. 温度单位混淆 → 误触发 90°C panic

`v < 1000` 就 `×1000` 当作"整度转毫度"。本机 `socd` zone 直接给 `49`（整度），
转换后 49000 恰好正确；但如果某个 zone 给 `900`（=90°C 的整度），
会被当成 0.9°C → `×1000` → 900000 → **误判 900°C 直接 panic**。

修：`v<1000` 整度、`1000<=v<=200000` 毫度、`>200000` 当坏值丢弃。

---

### 实测结果（本机 OPPO Find X8 Ultra / SM8750）

```
静止：3.07G → 2.22G → 1.55G → 1.15G → 748.8MHz   稳定，temp=49°C 不 panic
满载：need 6.48GHz → cap 顶到 3072000（cooling 物理上限）
FAVG：822528 / 998400 / 704914 kHz                 不再出现负值
功耗：595 / 1424 mW                                不再恒为 0
```

**注意**：大核真正能到的上限是 **3072000（3.07G）**，不是 3.53G。
3.53G 是 `cpuinfo_max_freq`，绕过 cooling 才能到，而本模块明确不碰 `scaling_max_freq`。


### 8. `current_now` 单位不是 µA（本机是 mA）

Android 惯例 `current_now` 是 µA，本机实测是 **mA**：

```
静置 215、满载 598      # 若是 µA 则满载只有 0.6mA，显然不可能
```

按 µA 算会小 1000 倍（598mA×3.8V 得出 2mW 而不是 2272mW）。
修：按数值量级判定（`>20000` 当 µA，否则当 mA），电压同理（`>1e6` 当 µV）。

### 9. 温度阈值 90°C 与官方 trip point 冲突

本机 `thermal_zone1 (cpu-0-0-0)` 的 trip point：

```
105000 / 118000 / 120000 / 125000 / 135000   (m°C)
```

满载压测时 `cpu-1-1-1` **稳定在 105°C** —— 这是官方设计工况。
旧 `T_PANIC=90000`（90°C）会在满载时直接 `release_all`，
等于"一满载就完全不限频"，与模块目的相反。

修：对齐官方 trip point —— 78°C 起软增益、100°C 压到 55%、112°C 才让路。

---

### 最终实测（V1.4fix2）

```
静止：  748.8MHz / 51°C / 730mW / load≈20%
满载：  3072MHz（cooling 上限）/ 105.3°C / 8.7W / load=100%
回落：  负载结束 8s 内回到 748.8MHz（temp 105->51°C）
```

| 指标 | 修复前 | 修复后 |
|---|---|---|
| FAVG_B | **-59 kHz**（溢出） | 806400 / 812308 kHz |
| power | 恒 0 mW | 730 / 8700 mW |
| 静止 cap | 3072000 不降 | 748800 稳定 |
| 满载 cap | 748800 不升 | 3072000 |
| temp | 误 panic | 105.3°C 正常 |

## 十一、probe.sh：从"手工抄表"改成"自动生成"

### 为什么要改

V1.4 之前 probe.sh 只打印表格，然后让用户手工把 32 行数字抄进两个 conf。
实测这套流程出过两次问题：

1. V1.3 的 map 表就是手工抄错的（把 state0 写成"不干预"，实际是最高档）
2. V1.4 的 map 表干脆是**凭空编的**（声称 748800 不存在、超大核压不下去）

只要还有"手工转录"这一步，就会继续错。改成自动生成 + 自动写入。

### 归属判定：怎么知道哪个 cooling_device 管哪个簇

不能按 `cooling_device0/1` 硬编码（不同机型编号不同）。做法：

```
1. 记下 baseline：policy0/scaling_max_freq 与 policy6/scaling_max_freq
2. 把该 cooling 写到中档 state（max_state/2）
3. 再读两个 policy：
     只有 policy0 变了 -> 这个 cooling 管大核
     只有 policy6 变了 -> 这个 cooling 管超大核
     都没变 / 都变了 -> 跳过并报警
4. state 归 0
```

### 采样时序竞态（必须处理）

cooling→cpufreq 的联动**不是同步的**。实测：

```
echo 0 > cooling_device0/cur_state; sleep 0.15; cat scaling_max_freq
  -> 3072000     (正确)
echo 2 > cooling_device0/cur_state; sleep 0.15; cat scaling_max_freq
  -> 3072000     (错误！还是上一档)
echo 0 > ...; sleep 0.15; cat scaling_max_freq
  -> 3532800     (错误！读到更高档)
```

第一版直接 `usleep 150000` 就采，生成的表里 `state0 = 3532800`、`state1 = 3321600`
——**比冷却允许的最高值还高**，明显是采到了过渡态。

修法 `set_state()`：写完 state 后轮询，**连续 3 次读到相同值**才采纳，最多等 3 秒。
改完后生成结果与手工逐档实测**逐字节一致**。

### 其它自动检查

- `time_in_state` 的 Σticks / Σ(f×j) 规模，超过 2.1e9 时提示「必须用 awk」
- 功耗节点单位判定：`current_now > 20000` 当 µA，否则当 mA；电压 `>1e6` 当 µV
- 温区 trip point 与当前温度，用于校准 `T_SOFT/T_HARD/T_PANIC`
- 抢写进程扫描

### 用法

```bash
sh /data/adb/eta_sched/probe.sh             # 报告 + 询问后写入
sh /data/adb/eta_sched/probe.sh --dry-run   # 只看不写
sh /data/adb/eta_sched/probe.sh --yes       # 不问直接写
```

写入前自动备份 `*.bak.<时间戳>`，写完提示 `ctl.sh restart`。
